# MeshCom KISS File Transmission

`mc_kiss_transmission.py` is a small, portable Python utility for transferring **small text files** between two computers through MeshCom nodes using **KISS/TCP**.

It is designed for simple field and emergency-style operation where a short TXT or CSV file must be moved through the existing MeshCom radio network without requiring external Python packages.

The program can run on **Linux, Windows and macOS** and uses only the Python standard library.

> This utility is an application built on top of MeshCom. MeshCom, its firmware, radio network, KISS implementation and underlying protocol remain the work of the MeshCom project and its contributors.

The MeshCom project provides resilient text-based communication for amateur radio using LoRa and APRS. This utility uses the KISS/TCP interface exposed by MeshCom firmware to exchange application data between two Python endpoints.

## What the program does

The same Python file is used at both ends.

- **Sender mode** reads a small file, optionally compresses and encrypts it, splits it into small blocks, and sends the blocks through the local MeshCom node.
- **Receiver mode** listens through KISS/TCP, reconstructs the file, decrypts/decompresses it when required, verifies its SHA-256 digest, and saves it into the configured download directory.
- Before sending a file, the sender performs a simple **receiver readiness check** using `READY?` / `OKREADY`.
- Normal file records use the native MeshCom/APRS acknowledgement mechanism exposed through KISS.
- Duplicate DATA blocks are safely ignored when they contain the same data.
- A completed transfer is identified by its unique Transfer ID, which is also added to the saved filename.

The default allowed file types are `.txt` and `.csv`, and the default maximum original file size is **10 KiB**.

## Requirements

- Python 3.9 or newer is recommended.
- No external Python packages are required.
- One MeshCom node must be available to each computer through KISS/TCP.
- KISS and KISS transmission must be enabled on the MeshCom node.

At minimum, the MeshCom node must have:

```text
--kiss on
--kiss tx on
```

KISS/TCP normally uses port `8001`, unless the node or network setup uses another port.

Only one KISS client can use the relevant MeshCom KISS connection at a time, according to the operating constraints of the firmware/interface being used.

## Basic topology

```text
Computer A                     MeshCom network                     Computer B
-----------                                                       -----------
Python TX  <-> MeshCom A  <---- LoRa / MeshCom ---->  MeshCom B <-> Python RX
             KISS/TCP                                  KISS/TCP
```

The program does not replace MeshCom routing or radio operation. It uses MeshCom as the transport network.

## Preliminary READY? / OKREADY check

Before every new file transmission, endpoint A checks that the Python receiver is actually running at endpoint B.

```text
Endpoint A                                      Endpoint B
    |                                               |
    |--------------- READY? ----------------------->|
    |                                               | Python receiver is running
    |<-------------- OKREADY -----------------------|
    |                                               |
    |             start file transfer               |
```

The check is deliberately simple:

1. The sender creates a random 8-character Handshake ID.
2. It sends `MCF1|READY?|<handshake_id>` to the destination.
3. A running receiver answers with `MCF1|OKREADY|<handshake_id>`.
4. The sender accepts only an `OKREADY` from the expected source with the matching Handshake ID.
5. If no valid `OKREADY` arrives within `ack_timeout`, the sender tries again.
6. The number of handshake attempts is fixed in the Python code at **3**.
7. After three failures, the program aborts the operation **before START/DATA/END are transmitted**.

`READY?` and `OKREADY` are application service messages generated by this utility. They are intentionally unnumbered and are separate from the native acknowledgement process used for the actual file records.

After a successful readiness check, the handshake has no persistent state. A new `--send` operation performs a new readiness check.

## File-transfer protocol

The utility uses a small application protocol named `MCF1`.

### START

```text
S|transfer_id|filename_base64|original_size|transport_size|blocks|sha256|compressed|encrypted
```

START describes the incoming transfer: filename, sizes, number of blocks, SHA-256 digest and transport options.

### DATA

```text
D|transfer_id|sequence|payload_base64
```

Each DATA record contains one numbered block encoded with URL-safe Base64.

### END

```text
E|transfer_id|sha256
```

END tells the receiver that the transfer is complete and supplies the expected SHA-256 digest again.

## Reliability and acknowledgements

START, every DATA record, and END are sent as addressed and numbered APRS messages through KISS.

For each normal transfer record, the sender waits for:

1. a KISS TX-result reporting that the local MeshCom node accepted the transmission;
2. the corresponding native MeshCom/APRS end-to-end ACK.

If confirmation is not received, the same record is retried up to `max_retries` times.

**Important:** the same APRS/KISS message number is retained for every retry of the same logical record. This allows a delayed ACK to remain valid for the record that is being retried.

The `READY?` / `OKREADY` preliminary check is independent of this normal START/DATA/END acknowledgement mechanism.

## Compression

Compression is controlled by:

```json
"auto_compress": true
```

When enabled, the program tries zlib compression at level 9. The compressed representation is used **only when it is smaller than the original file**.

Therefore `auto_compress: true` does not force compression when it would increase the transmitted payload.

The sender reports the actual decision:

```text
Compression  : ZLIB
```

or:

```text
Compression  : NO
```

## Encryption

Encryption is optional. It is enabled by setting a non-empty password:

```json
"encryption_password": "your-password"
```

To disable encryption:

```json
"encryption_password": ""
```

The current implementation uses only Python standard-library primitives:

- PBKDF2-HMAC-SHA256 for key derivation;
- a random 16-byte salt;
- a random 16-byte nonce;
- an HMAC-SHA256-derived counter stream for encryption/decryption;
- HMAC-SHA256 for payload authentication.

The encrypted binary transport format is:

```text
salt(16) + nonce(16) + ciphertext + HMAC-SHA256(32)
```

`encryption_iterations` controls PBKDF2 iterations. The default is `200000` and the program rejects values below `10000`.

Both endpoints must use the same password for encrypted transfers. If the receiver has the wrong password, authentication/decryption fails and the file is not saved.

This is a custom standard-library construction used to avoid external dependencies; it should not be described as a standardized AEAD format such as AES-GCM or ChaCha20-Poly1305.

## Processing order

On the sender:

```text
original file
     |
     +--> optional zlib compression (only if smaller)
     |
     +--> optional encryption
     |
     +--> split into blocks
     |
     +--> URL-safe Base64
     |
     +--> MCF1 DATA records
     |
     +--> MeshCom KISS/TCP
```

On the receiver the operations are reversed. The reconstructed original data is finally checked against its SHA-256 digest before it is saved.

## Configuration

Example `meshcom_file.json`:

```json
{
    "meshcom_ip": "192.168.1.120",
    "meshcom_port": 8001,
    "mycall": "IU5AAA-1",
    "download_dir": "./received",
    "block_size": 60,
    "tx_interval": 3.0,
    "ack_timeout": 45.0,
    "tx_result_timeout": 5.0,
    "max_retries": 5,
    "max_file_size": 10240,
    "allowed_extensions": [".txt", ".csv"],
    "connect_timeout": 10.0,
    "show_packets": true,
    "auto_compress": true,
    "encryption_password": "",
    "encryption_iterations": 200000,
    "kiss_auth_password": ""
}
```

### Configuration parameters

| Parameter | Purpose |
|---|---|
| `meshcom_ip` | IP address or hostname of the local MeshCom KISS/TCP endpoint. |
| `meshcom_port` | KISS/TCP port. Default is normally `8001`. |
| `mycall` | Callsign used by this endpoint. The AX.25 base callsign must match the callsign configured in the MeshCom node. |
| `download_dir` | Directory where successfully received files are stored. |
| `block_size` | Raw DATA block size before Base64. Default `60`; accepted range `1..70`. |
| `tx_interval` | Delay in seconds between transfer operations/retries where applicable. |
| `ack_timeout` | Maximum wait for a normal native ACK. It is also the timeout for each preliminary `OKREADY` attempt. |
| `tx_result_timeout` | Maximum wait for the local KISS TX-result during normal START/DATA/END transmission. |
| `max_retries` | Maximum retries for each normal START/DATA/END record. It does **not** control the preliminary handshake, which always uses 3 attempts. |
| `max_file_size` | Maximum accepted original file size in bytes. Default `10240`. |
| `allowed_extensions` | File extensions allowed for transmission/reception. |
| `connect_timeout` | TCP connection timeout in seconds. |
| `show_packets` | Enables additional packet/ACK diagnostic output. |
| `auto_compress` | Enables dynamic zlib compression when compression reduces payload size. |
| `encryption_password` | Password used for encryption. Empty string disables encryption. |
| `encryption_iterations` | PBKDF2-HMAC-SHA256 iteration count. Default `200000`. |
| `kiss_auth_password` | Optional password for KISS authentication if the MeshCom firmware/interface is configured to require it. |

## Callsign requirements

The source AX.25 callsign is validated by the program.

- Base callsign: maximum 6 alphanumeric characters.
- Source SSID: `0..15`.
- The base callsign must match the base callsign configured on the local MeshCom node.
- The textual destination used as the APRS addressee is limited to 9 characters by this utility.

Example:

```json
"mycall": "IU5ABC-1"
```

## Running the receiver

Start the program on endpoint B before transmitting:

```bash
python mc_kiss_transmission.py --config meshcom_file.json --receive
```

The receiver connects to its configured MeshCom KISS/TCP endpoint and remains active until `CTRL+C`.

When it receives `READY?`, it immediately returns the matching `OKREADY`. Normal START/DATA/END records are then processed as they arrive.

## Sending a file

On endpoint A:

```bash
python mc_kiss_transmission.py --config meshcom_file.json --to IK5XMK-12 --send file.txt
```

The program first checks the destination receiver with `READY?` / `OKREADY`.

If the receiver answers, file transmission begins. If the receiver does not answer after three attempts, the operation is aborted and no START/DATA/END records are sent.

## Received filenames

A successfully reconstructed file is saved with its Transfer ID added to the filename.

Example:

```text
list.txt
```

may be stored as:

```text
list_C318718A.txt
```

This allows separate transfers of files with the same original name to remain distinguishable.

## Integrity checks

Before a received file is saved, the program verifies:

- all expected DATA blocks are present;
- reconstructed transport size matches the START metadata;
- decryption/authentication succeeds when encryption is enabled;
- decompression succeeds when compression was used;
- final original size is correct;
- SHA-256 matches the digest announced by the sender.

If these checks fail, the incomplete or invalid file is not saved.

## Intended use

This utility is intended for **small text-oriented transfers**, for example:

- short TXT documents;
- small CSV lists;
- small operational or field data files;
- simple emergency/portable information exchange where MeshCom connectivity is available.

It is deliberately not designed as a general-purpose large-file transfer protocol. Small blocks, controlled pacing and conservative retry behavior are used to respect the limited capacity of a LoRa mesh network.
